# ADR-0032: Schedulerの実行主体を埋込ホストへ委譲する（Port化）

- **ステータス**: Accepted
- **関連要件**: FR-EXE-006（Scheduler）と、それに従属する FR-PRV-006 / FR-CAP-016 / FR-SEC-002 / NFR-SEC-003 / NFR-DAT-001
- **関連する設計書**: 01_要件定義.md FR-EXE-006, 02_システム仕様.md 2.4（モジュール責務）, 03_基本設計.md 3.15（DI方針）, 05_シーケンス設計.md 5.10（Health Check）
- **検出**: P11 総合検証（P11-D2）

## コンテキスト

FR-EXE-006 は「Scheduler（Batch実行計画、Health Check周期実行、Rotation周期実行）を提供すること」を
必須（M）要件としている。しかし**誰がその周期実行のスレッドを持つのか**が設計書のどこにも書かれていない。

これは単なる未実装ではなく、既存の設計方針と正面から衝突する論点である。

- CLAUDE.md 不変条件6 / 03_基本設計.md 3.15: `apap-runtime` とその依存モジュールに
  DIコンテナ・アプリフレームワーク・ロギング実装を持ち込まない（埋込先と競合させないため）。
- `apap-runtime` は**埋込ライブラリ**であり、ホスト（prompt-engine等）のプロセス内で動く。
  ライブラリが勝手に常駐スレッドやスケジューラスレッドプールを起動すると、
  ホストのライフサイクル管理（起動順序・シャットダウン・スレッド数の制御）と衝突する。
- 一方 `gateway/apap-gateway` は常駐プロセスなので周期実行の主体になりうるが、
  Gatewayは「HTTP層の薄いアダプタに徹し、ビジネスロジックを置かない」制約下にある。
  Health Check周期実行やRotation期日管理はビジネスロジックであり、Gatewayに置けない。

結果として現在、Schedulerは存在せず、次の要件が**構造的にブロックされている**。

| 要件 | ブロックされている内容 |
|---|---|
| FR-PRV-006 | Providerの定期健全性監視。`ProviderHealthAggregator`/`HealthCheckService`は実装済みだが周期起動されず、`ProviderHealthChanged`が一度も発火しない |
| FR-CAP-016 | Batchジョブの実行計画。永続化層のみ実装済みで実行フローが無い |
| FR-SEC-002 | Credential Rotationの期日到来検知 |
| NFR-SEC-003 | 監査ログの既定400日での自動失効・削除 |
| NFR-DAT-001 | Conversation履歴の既定90日での自動削除 |

## 決定

**Schedulerを`apap-runtime`の中に実装しない。** 周期実行の起動主体は埋込ホスト（またはGateway）とし、
APAPは「何を・どの間隔で実行すべきか」を宣言するPortと、その実体である**冪等な実行単位**のみを提供する。

1. `apap-domain` に `ScheduledTask`（`name`, `interval`, `suspend fun runOnce()`）と、
   それらを列挙する `ScheduledTaskRegistry` を定義する。
2. `ApapEngine` に `scheduledTasks: List<ScheduledTask>` を公開する。ホストは自分のスケジューラ
   （Spring の `@Scheduled`、Kubernetes CronJob、独自のコルーチンループ等）からこれを駆動する。
3. `gateway/apap-gateway` は常駐プロセスとして**既定の駆動実装**を1つ持つ（コルーチンによる
   単純な固定間隔ループ）。これはビジネスロジックではなく「ホストとしての起動責務」であり、
   Gatewayの制約に抵触しない。`ApapEngine.scheduledTasks` を回すだけで、何を実行するかは知らない。
4. 各 `runOnce()` は**多重起動に対して冪等**であることを要件とする。排他が本質的に必要な
   タスク（削除ジョブ等）は、`EventStoreRepository` の楽観ロックと同じくストア側の
   条件付き更新で自衛する。

   **設計書との関係**: 05_シーケンス設計.md 5.10 は「リーダー選出済ノードのみ実行(30秒周期)」と
   明記しており、リーダー選出を前提としている。本ADRはそれを否定しない——リーダー選出は
   別課題として残す（下記「未決定のまま残る事項」）。ただし**リーダー選出があっても冪等性は必要**である。
   リーダーの切り替わり中やネットワーク分断中には二重実行が起こりうるため、
   リーダー選出を「二重実行が起きない保証」として扱うと、まさに本プロジェクトが繰り返している
   「機構があること」と「機構が効いていること」の混同になる。冪等性を先に要件化し、
   リーダー選出は負荷削減（全PodがProviderへhealthCheckを打たない）のための最適化として後から入れる。

## 影響（Consequences）

- 埋込ホストは「APAPを組み込んだだけでは周期処理が動かない」ことを知る必要がある。
  `docs/integration/prompt-engine.md` に、`scheduledTasks` を駆動しない場合に
  **何が動かないか**（上表）を明記する。これを書かないと、ホスト側は
  「Health Checkは動いているはず」と誤解する——本プロジェクトが繰り返し踏んだ失敗の形そのもの。
- 「ホストが駆動しなかった場合」が正常系として存在するため、`ApapHealth`（`/readyz`）は
  Provider Healthの鮮度（最終更新時刻）を持ち、一度も更新されていない状態を
  「UP」と偽らないようにする必要がある。
- Gatewayに既定駆動を置くため、Gatewayの起動・停止シーケンス（ADR相当の実装は
  `GatewayLifecycle`）に周期タスクの停止を追加する必要がある。

## 未決定のまま残る事項

- リーダー選出の実現方式（5.10が要求）。ADR-0001でRedisを分散状態ストアとして選定済みのため
  そこにリースを置く形が有力だが、`apap-runtime`は`apap-infrastructure-distributed`に
  依存しない方針であり、リーダー選出をどのレイヤに置くかは別途決める必要がある。
- 複数Pod構成でのBatchジョブ二重実行を、ジョブ側の状態遷移（`BatchJob` Aggregate、9章の遷移表）で
  弾くかどうか。冪等性の実現手段として有力だが、実装時に確定する。
- 5.10が定める30秒周期を既定値とするか。他のタスク（Rotation期日、保持期間削除）の既定間隔は
  設計書に記載が無く、タスク追加時にこのADRへ追記する。
