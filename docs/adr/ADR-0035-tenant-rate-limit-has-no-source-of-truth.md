# ADR-0035: テナント別レート制限に設定元が無い（既定バケットは絞らない）

- **ステータス**: Accepted
- **関連要件**: FR-EXE-003（Rate Limiter: Provider制限の遵守 + テナント別制限）, NFR-PRF-003
- **関連する設計書**: 02_システム仕様.md 2.4（Rate Limiter）, 2.6.2（Provider `rate_limits{rpm,tpm,concurrent}`）, 2.10 step 205（入口Rate Limit（テナント））
- **検出**: P12 是正作業（P11-F10の修正中に判明）

## コンテキスト

`RateLimiter`は2段のスコープを持つ（`RateLimitScope.TenantScope` / `ProviderScope`）。
Provider側は 2.6.2 が `rate_limits{rpm, tpm, concurrent}` を定義しており、
Provider登録時の値をそのままバケット設定へ反映できる（P12でその配線を実装した）。

**しかしテナント側には設定元がどこにも無い。** 設計書は 2.10 の処理順序で
「入口Rate Limit（テナント）」を要求するが、その上限値をどのエンティティが持つのかを
定めていない。12_ER図.md にもテナントのレート上限に相当するカラムは無く、
`QuotaPolicy` は期間あたりのリクエスト数・トークン数・コストの**予算**であって
秒あたりのレートではない。

その結果、実装は`RateLimiterConfig`の既定値をテナントスコープへ適用していた。
既定値は**容量60・毎秒1トークン補充**だったため、次が起きていた。

- 全テナントが、設定した覚えのない「毎秒1リクエスト」の制限を受ける
- P11のベンチマークで出荷時スループットが 4.7 req/s だった直接の原因
  （Providerの`rpm`を600に設定していても、テナント側の既定が先に効く）
- しかも失敗の形が「429で拒否」ではなく「待たされる」ため、
  **遅いのか絞られているのかが利用側から区別できない**

「テナント別制限が実装されている」ことと「テナント別制限が設定できる」ことは別で、
後者が無いまま前者の既定値だけが効いていた。

CLAUDE.md 不変条件8の判断基準では、この曖昧さの解釈次第で FR-EXE-003 の
「テナント別制限」が満たせないため、ADRを起票する。

## 決定

1. **未設定スコープの既定バケットは絞らない。** `RateLimiterConfig`の既定を
   実質無制限（容量100,000・毎秒100,000補充）へ変更する。
   絞る根拠を持たないスコープを既定値で絞ると、意図しない全体スロットルになり、
   かつ「レート制限が効いている」と誤認させる。**根拠のある制限だけを課す。**
2. **Providerスコープは`Provider.rateLimits.rpm`から自動設定する**
   （`ProviderRateLimitConfigurer`）。容量`rpm`・毎秒`rpm/60`補充とし、
   1分ぶんのバーストを許容しつつ定常レートを`rpm`に一致させる。
3. **テナント別制限は当面、埋込ホストが明示的に設定する**。
   `ApapEngineBuilder.rateLimits(capacity, refillPerSecond)` で既定バケットを上書きできる。
   これはテナント横断で同一の値になるため、テナントごとに変えたい場合は満たせない。
4. ドメインにテナント別レート上限を持たせるかどうかは**本ADRでは決めない**。
   置き場所の候補（`QuotaPolicy`への追加 / `TenantEntitlement`への追加 / 新Aggregate）は
   いずれも12_ER図.mdの変更を伴い、設計書側の判断が要る。

## 影響（Consequences）

- FR-EXE-003 は「Provider制限の遵守」は満たすが、「テナント別制限」は
  **テナントごとに異なる値を設定できない**という形で部分実装のまま残る。
  `docs/traceability/requirements-matrix.md` にその旨を記載する。
- 既定が実質無制限になるため、**レート制限は明示的に設定しない限り掛からない**。
  これは「知らないうちに絞られる」より安全側だが、
  マルチテナントで特定テナントの暴走を止めたい運用では設定が必須になる。
  `docs/integration/prompt-engine.md` に明記する。
- `tpm`（トークン数/分）と`concurrent`（同時実行数）は現在のトークンバケットでは
  表現できないため、Provider側も`rpm`しか反映されない。これも既知の未対応として記載する。

## 未決定のまま残る事項

- テナント別レート上限の置き場所（上記4）。
- `tpm`/`concurrent`の実現方式。前者はトークン数を`cost`として消費する形で
  同じバケット機構に載せられる可能性がある。後者はセマフォ的な別機構が要る。
