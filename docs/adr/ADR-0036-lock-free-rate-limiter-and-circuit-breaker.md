# ADR-0036: Rate LimiterとCircuit Breakerのロック競合への対処方針（CAS化は単独では採らない）

- **ステータス**: Accepted
- **関連要件**: NFR-PRF-003（スループット 1,000 req/s / ノード）, NFR-AVL-003（ステートレス水平スケール）
- **関連する設計書**: 02_システム仕様.md 2.4（Rate Limiter）, 2.12（Circuit Breaker）
- **検出**: P12 総合検証のプロファイリング / P13 で方針を決定

## コンテキスト

P12のスループット計測中にスレッド状態をサンプリングしたところ、BLOCKEDスレッドが
並列度とともに増えた（並列度1で0、8で93、64で1,046サンプル）。頻出フレームは
`DefaultQuotaManager.checkAndReserve` / `commit` と `CircuitBreaker.tryAcquire` /
`recordSuccess` に集中しており、**共有状態の排他がボトルネック候補である**ことは分かった。

ただし現時点でBLOCKEDは全サンプルの約4.5%（1,046 / 23,140）に留まり、
**律速だと断定する根拠は無い**。さらに計測ハーネス自体が400〜600 req/s で飽和しており
（クライアントとサーバが同一の8コアJVMを共有）、エンジンの上限を測れていない。

一方で、ロック競合は負荷に対して**超線形に増える**性質がある。現在4.5%でも
高負荷では律速になり得るため、「今は問題ない」で放置すると、
分離環境で再計測した瞬間に設計変更を迫られる可能性がある。そこで
「CASでロックなしにできるか」を先に検討し、結論を残す。

## 検討: CAS化は技術的に可能か

**可能である。** ただし対象ごとに事情が異なる。

### Token Bucket（`TokenBucketRateLimiter`）

現在は `tryAcquire` / `estimateWaitMillis` が `@Synchronized` で、
`RateLimitCounterStore` に対する find → 補充計算 → 消費 → save の read-modify-write を保護している。

状態 `TokenBucketState(tokens, lastRefillAt, capacity, refillPerSecond)` は不変オブジェクトなので、
スコープごとに `AtomicReference<TokenBucketState>` を持ち
「読む → 補充と消費を計算 → `compareAndSet`、失敗したら再試行」の標準的なロックフリー
トークンバケットにできる。In-Memory実装では素直に適用できる。

**ただしPortの形が合わない。** `RateLimitCounterStore` は `find` / `save` の2操作で、
その間に他スレッドが割り込める。CAS化するにはPortに
「比較して入れ替える」または「原子的に1つ消費する」操作が要る。
そして分散実装（Redis、ADR-0001）では**CASではなくLuaスクリプト**が正しい原語である
——ネットワーク往復を挟むCASはリトライのたびにRTTを払い、競合下で急速に悪化する。

### Circuit Breaker

30秒窓の失敗率を見るため、状態遷移と件数更新の両方が要る。
`CircuitBreakerState` を不変にして `AtomicReference` + CAS で遷移させ、
件数は窓ごとの不変スナップショットを差し替える形にすればロックフリーにできる。
遷移条件の評価と遷移の適用を1回のCASにまとめる必要がある（読んでから書くまでに
別スレッドがOPENへ遷移させている可能性があるため）。

### CAS化の限界

**CASはロックの万能な置き換えではない。** 競合が単一のホットキー
（1テナント・1Provider）へ集中する場合、CASはスピンして失敗し続け、
ロックより悪化することがある。本件の競合はまさにスコープ単位——
つまり単一キーに集中する形——なので、CAS化だけでは効かない可能性が高い。

構造的に効くのは次の2つで、CAS化はその後の最適化として意味を持つ。

1. **キー単位のストライピング**: スコープのハッシュでシャードし、競合そのものを分散する。
2. **クリティカルセクションの削減**: 1リクエストあたりの排他回数を減らす。
   現在はテナントスコープとProviderスコープで2回、CBで取得・成功記録・失敗記録が別々に入る。

## 決定

1. **今はCAS化しない。** 効果を測れない状態で、正しさの検証が難しい並行実装
   （ABA問題、遷移条件とCASの原子性、窓の一貫性）へ置き換えるのは割に合わない。
   「機構を入れたが効いていない」を増やすだけになる。
2. **先に分離環境で再計測する**（`docs/verification-report.md` 3.6の条件）。
   その計測で **ロック競合率（BLOCKED比率）を測定指標に含める**。
   競合が律速だと確認できてから、上記の1（ストライピング）→2（回数削減）→CAS化 の順に検討する。
3. **Portの形だけ先に将来へ備えない。** `RateLimitCounterStore` に
   `compareAndSet` や `tryConsume` を今足しても、実装が伴わなければ
   「使われない逃げ道」が増えるだけである（本プロジェクトが繰り返した失敗の形）。
   必要になった時点で、In-MemoryとRedisの両方の実装と同時に入れる。

## 影響（Consequences）

- NFR-PRF-003 は「本構成では判定不能」のまま残る。分離環境での再計測が前提条件になる。
- 高負荷でロック競合が律速だと判明した場合、`RateLimitCounterStore` /
  `CircuitBreakerStateStore` のPort変更を伴う。**Portを変えるということは
  分散実装（Redis）も同時に変えるということ**であり、片方だけの最適化はしない。
- この判断は「競合は存在するが律速と確認されていない」という現時点の観測に基づく。
  再計測で覆る可能性があり、そのときは本ADRをSupersedeする。
