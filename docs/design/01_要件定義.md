# 1. 要件定義

AI Provider Abstraction Platform（APAP）設計書 第1章

---

## 1.1 概要

AI Provider Abstraction Platform（以下 APAP）は、AIを利用するすべてのシステム（AI Agent、Workflow Engine、Backend API、Web/Mobile/Desktop Application、IoT、CLI、Batch、管理システム）に対し、**特定のAI Providerに依存しない共通抽象化インターフェース**を提供するプラットフォームである。

APAPは各AI Provider固有のAPI仕様・認証方式・リクエスト/レスポンス形式・レート制限・エラー体系を **Provider Adapter** 内に完全に閉じ込め、利用側には **Capability（能力）単位の統一API** のみを公開する。利用側は「どのProviderのどのModelを使うか」を意識せず、「何をしたいか（Capability）」と「どのような条件で実行したいか（Policy）」のみを指定する。

APAPは関連基盤との間で以下の責務分担を持つ。

| 基盤 | 責務 |
|---|---|
| AACP（AI Agent Common Platform） | AIエージェントの実行・ワークフロー・エージェントメモリの管理（AIの「使い方」） |
| CIAP（Common Identity & Access Platform） | 認証・認可・ユーザー管理 |
| **APAP（本設計対象）** | **AI Provider / Modelの抽象化、ルーティング、フォールバック、コスト管理、監視（AIを提供する「相手」の抽象化）** |

| # | 目的 | 実現手段 |
|---|---|---|

| G-02 | Model変更をアプリケーションへ無影響で実現 | Model Alias + Model Registry + Routing Policy |

| G-05 | 可用性の確保 | Retry / Fallback / Circuit Breaker / Load Balancer / Provider Health |
| G-06 | 拡張性の確保 | Plugin Manager / Adapter SPI / Policy SPI |
| G-07 | 保守性の確保 | Clean Architecture / DDD / SOLID / Provider毎の独立モジュール |
| G-08 | 可観測性の確保 | Metrics / Tracing / Audit Log / Health Check / Usage Analytics |
| G-09 | セキュリティの確保 | API Key管理 / Secret管理 / 暗号化 / Credential Rotation / Provider Isolation |

## 1.4 対象外

| 対象外 | 理由 / 代替 |
|---|---|
| AI Agentの実装（計画・推論ループ等） | AACPの責務 |
| Workflowの実装（DAG定義・実行制御） | Workflow Engineの責務 |
| 業務ロジック | 利用側アプリケーションの責務 |
| 画面設計・管理画面UI | 本書はAPIまで。UIは別設計 |
| エンドユーザー認証・認可・ユーザー管理 | CIAPの責務（APAPはCIAP発行トークンを検証するのみ） |
| AI Providerそのものの構築・モデル学習基盤 | 外部Provider / 別基盤の責務（Fine Tuning APIの抽象化のみ将来対象） |

## 1.5 利用シナリオ

| # | シナリオ | 流れ |
|---|---|---|
| S-01 | チャットアプリがAI応答を取得 | App → `POST /v1/chat` → APAPがCapability=Chatで最適Provider/Modelを選択 → 正規化応答を返却 |
| S-02 | Provider障害時の無停止継続 | Primary Provider障害 → Circuit Breaker Open → Fallback Chainに従いSecondaryへ自動切替。利用側は無変更・無感知 |
| S-03 | 新Provider追加 | 運用者がAdapter Pluginを配置しAdmin APIでProvider登録 → Routing Policy更新 → 利用側変更ゼロで新Provider利用開始 |
| S-04 | Model世代交代 | Alias `chat-standard` の参照先を新Modelへ変更（Canaryで10%→50%→100%） → 利用側はAlias指定のため無変更 |
| S-05 | コスト超過の自動制御 | Cost EngineがBudget閾値超過を検知 → `CostThresholdExceeded` イベント発火 → Routing Policyが低コストModelへ自動切替 or 拒否 |
| S-06 | Workflow Engineの一括Embedding | Batch APIへ10万件投入 → SchedulerがRate Limit内で分割実行 → 完了イベント通知 |
| S-07 | ストリーミング応答 | App → SSE接続 → APAPがProviderのストリームを正規化チャンクへ変換し中継 |
| S-08 | AI AgentのTool Calling | Agent → Tool定義付きChat要求 → APAPが共通Tool形式をProvider固有形式へ変換 → ToolCall要求を正規化して返却 → Agentが実行結果を返信 |
| S-09 | 会話の継続 | AppがConversation IDを指定 → Context Managerが履歴を復元しトークン上限内へ圧縮してPromptに合成 |
| S-10 | リージョン制約下での実行 | Policy `region=jp` を指定 → Routing Engineが国内リージョンのProviderのみを候補化 |

| UC-17 | Conversation管理 | 利用システム | Session確立済 | 会話作成/継続/履歴取得/削除 | 履歴永続化 |
