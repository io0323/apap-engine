## 2.1 全体構成

```
+---------------------------------------------------------------+
| 利用システム                                                    |
| AI Agent / Workflow Engine / Backend / Web / Mobile /          |
| Desktop / IoT / CLI / Batch / 管理システム                       |
+------------------------------+--------------------------------+
                               | REST / gRPC / SSE / SDK
                               v
+---------------------------------------------------------------+
| AI Gateway（API受付・認証検証・レート制御・ルーティング入口）        |
+------------------------------+--------------------------------+
                               v
+---------------------------------------------------------------+
| Application Core                                               |
|  Capability Resolver → Routing Engine → Execution Engine       |
|  Prompt Engine / Context・Conversation・Session Manager         |
|  Retry / Fallback / Circuit Breaker / Cache / Rate Limiter     |
+------------------------------+--------------------------------+
                               v
+---------------------------------------------------------------+
| Provider Adapter Layer（Plugin）                                |
|  Adapter A | Adapter B | Adapter C | ...（Provider毎に独立）     |
+------------------------------+--------------------------------+
                               v
                        外部 AI Provider群

横断基盤: Provider Manager / Model Manager / Plugin Manager /
          Cost Engine / Audit Engine / Monitoring Engine /
          Secret Store / Event Bus / Scheduler
```

## 2.2 アーキテクチャ

### 2.2.1 アーキテクチャ原則

| 原則 | 適用 |
|---|---|
| Provider / Model Independent | 利用側APIにProvider・物理Model名を露出しない（Alias / Capabilityのみ） |
| Capability Driven | APIはCapability単位。Capability Registryが唯一のスキーマ源 |
| API First | OpenAPI / Protobuf定義を先行し、SDKは定義から生成 |
| Plugin Architecture | Adapter / Policy / Cache / Retry / Monitoring をSPIで差替可能 |
| Event Driven | 状態変化はドメインイベントとしてEvent Busへ発行。監査・分析・コストは購読側で処理 |
| Cloud Native | ステートレスなコア、コンテナ化、宣言的設定、水平スケール |
| DDD + Clean Architecture | Bounded Context分割、依存は内向き一方向 |
| SOLID | 各章のクラス設計に反映（3章参照） |
| CQRS | 実行系（Command: AI実行）と参照系（Query: Analytics / Discovery）を分離。参照系はイベントから構築したRead Modelを使用 |
| Event Sourcing | Provider / Model / Policyの構成変更、およびBatchジョブ状態はイベントソーシングで管理（AuditLogと監査再現性を両立）。AI実行リクエスト自体はイベントソーシング対象外（高頻度のためAudit Logで記録） |

### 2.2.2 レイヤ構成

| レイヤ | 内容 | 依存先 |
|---|---|---|
| Presentation | REST / gRPC / SSE Controller、Request/Response DTO、認証フィルタ | Application |
| Application | UseCase（Command / Query Handler）、トランザクション境界、イベント発行 | Domain |
| Domain | Entity / Aggregate / Value Object / Domain Service / Domain Event / Repository Interface / Adapter Port（SPI Interface） | なし（最内層） |
| Infrastructure | Repository実装、Event Bus実装、Secret Store実装、Cache実装、Metrics実装 | Domain（Interfaceの実装） |
| Provider Adapter | Adapter SPI実装（Provider毎Plugin）。Domain定義のPortを実装 | Domain Port（実装）+ 外部Provider SDK/HTTP |

依存規則: Presentation → Application → Domain ← Infrastructure / Adapter（依存性逆転）。

## 2.5 Routing仕様

### 2.5.1 入力

RoutingRequest = { capability_id, model_alias?, tenant_id, constraints{ region?, max_cost?, max_latency_ms?, exclude_providers[]? }, preferences{ optimize_for: cost \| latency \| quality \| balanced }, conversation_id? }

### 2.5.2 決定手順（確定仕様）

1. **候補抽出**: Capability Resolverが `capability_id` を満たす (Provider, Model) 集合を取得。`model_alias` 指定時はAlias解決結果（Canary比率含む）で絞込。
2. **ハードフィルタ**（不合格は除外、順序固定）:
   a. Provider Status = ACTIVE かつ Model Status = ACTIVE（TESTINGはCanary対象時のみ）
   b. Circuit Breaker が OPEN でない
   c. Provider Health ≠ DOWN
   d. Region制約（constraints.region ⊆ model.regions）
   e. Policy禁止事項（4階層すべての deny を評価）
   f. テナントのCapability/Model利用権限
   g. Quota残量 > 0
3. **スコアリング**: 残候補へ重み付き合成スコアを計算。
   `score = w_cost×S_cost + w_latency×S_latency + w_avail×S_avail + w_priority×S_priority`
   - S_cost = 1 − normalize(推定コスト)（推定コスト = 入力推定トークン×入力単価 + max_tokens×出力単価）
   - S_latency = 1 − normalize(直近5分のp90レイテンシ、Health Storeから取得)
   - S_avail = 直近5分の成功率 ×（Health=UP:1.0, DEGRADED:0.5）
   - S_priority = Provider.priority と Model.priority の正規化値
   - 重み既定値: balanced = (0.25, 0.25, 0.30, 0.20)。optimize_for=cost → (0.55, 0.10, 0.25, 0.10)、latency → (0.10, 0.55, 0.25, 0.10)、quality → (0.05, 0.10, 0.25, 0.60)。Policyで上書き可。
4. **Sticky補正**: conversation_id があり直前Turnと同一候補が残存する場合、その候補スコアへ +0.05。
5. **Load Balancing**: 最高スコアとの差が 0.02 以内の候補群に対し、重み付きラウンドロビンで1つ選択。
6. **Fallback Chain構築**: スコア降順で最大 `fallback_depth`（既定3）件をChainとして確定。
7. **決定記録**: RoutingDecision{ 候補一覧, スコア, 適用Policy ID, 選択理由 } をAuditへ発行。

### 2.5.3 Policy階層

| 階層 | 設定者 | 例 | 優先度 |
|---|---|---|---|
| Platform Policy | 運用者 | 全テナント共通のProvider禁止、既定重み | 最上位（deny不可逆） |
| Tenant Policy | テナント管理者 | リージョン限定、Budget、優先Provider | ↑を継承 |
| Workflow Policy | Workflow定義 | 特定StepはStructured Output必須Model | ↑を継承 |
| User Preference | 利用リクエスト | optimize_for, model_alias | 最下位（allowの範囲内でのみ有効） |

解決規則: **deny は上位が絶対**（下位で覆せない）。**allow / 重み / 選好は下位が上書き**。

## 2.6 Provider管理仕様

### 2.6.1 Provider状態遷移

`REGISTERED → VALIDATING → ACTIVE ⇄ SUSPENDED、ACTIVE → DRAINING → DISABLED → (論理)DELETED`

| 状態 | 意味 | ルーティング対象 |
|---|---|---|
| REGISTERED | 登録済・未検証 | 対象外 |
| VALIDATING | Credential・疎通・Capability検証中 | 対象外 |
| ACTIVE | 稼働中 | 対象 |
| SUSPENDED | 一時停止（障害・手動） | 対象外（自動復帰可） |
| DRAINING | 新規停止・実行中完遂待ち | 新規対象外 |
| DISABLED | 無効 | 対象外 |
| DELETED | 論理削除 | 対象外（履歴保持） |

### 2.6.2 Provider登録情報

Provider{ provider_id, name, adapter_plugin_id, adapter_spi_version, endpoints[]{region, base_url}, auth_type（SPI準拠の抽象型: api_key / oauth2_client_credentials / signed_request / custom）, credential_refs[]（Secret Store参照のみ、値は保持しない）, rate_limits{rpm, tpm, concurrent}, priority(1-100), regions[], tags[], status }

### 2.6.3 Provider Health

- Schedulerが既定30秒間隔で `adapter.healthCheck()` を実行（軽量疎通 + 認証検証）。
- 実トラフィックの成功率/レイテンシを併用（パッシブヘルス）。
- 判定: 成功率 ≥ 99% → UP、90–99% または p90悪化2倍 → DEGRADED、連続3回probe失敗 または 成功率 < 90% → DOWN。
- 状態変化時 `ProviderHealthChanged` 発火 → Routing Engineへ即時反映。

## 2.7 Model管理仕様

- Model{ model_id, provider_id, model_name（Provider内識別子）, version, capabilities[]{capability_id, 制約}, context_window, max_output_tokens, pricing{input_per_1k, output_per_1k, currency, effective_from}, regions[], status, priority }
- Model Status: `REGISTERED → TESTING → ACTIVE → DEPRECATED → RETIRED`。DEPRECATEDは既存Alias参照のみ許可（新規Alias付与不可）、RETIREDはルーティング対象外。
- **Alias**: Alias{ alias_id, name（例: `chat-standard`）, targets[]{model_id, weight%} }。weight合計=100。Canaryはweight操作で実現（例: 新Model 10% / 旧90%）。
- **Model Discovery**: Schedulerが日次で `adapter.discoverModels()` を実行し、差分を `ModelDiscovered` イベントとして通知。自動登録はせず、運用者承認後に登録（TESTING状態で開始）。

## 2.8 Request Flow（非Streaming）

```
1. Gateway: 受信 → TLS終端 → CIAPトークン検証 → tenant解決
   → RequestID/TraceID付与 → 入口Rate Limit（テナント）
2. Session/Conversation解決（指定時）: 履歴ロード
3. Prompt Engine: Validation → Optimization → Rendering（CanonicalPrompt生成）
4. Cache Engine: Request Cache照会（冪等キー）→ Response Cache照会
   （cacheable かつ hit なら 12へ短絡）
5. Capability Resolver: 候補集合算出
6. Routing Engine: フィルタ → スコア → Chain確定（RoutingDecision）
7. Quota Manager: 事前チェック（推定トークン）
8. Execution Engine: Chain先頭候補で実行開始
   8a. Circuit Breaker通過確認
   8b. Provider別Rate Limiter取得（待機 or 即時）
   8c. Request Mapper: CanonicalRequest → Adapter入力
   8d. Adapter呼出（タイムアウト予算内）
   8e. 失敗時: Retry Engine判定（同一候補内リトライ）
       → 尽きたら Fallback Engine（次候補へ、3へは戻らず8aから）
9. Response Mapper: 正規化（content / finish_reason / usage / error）
10. Cost Engine: コスト算出 → Usage記録（非同期）
11. Conversation Manager: Turn永続化（指定時）
12. Gateway: 共通Response返却
＊ 全過程でイベント発火: RequestReceived / RequestStarted /
   RequestCompleted / RequestFailed 等（14章）
```

## 2.9 Response Flow

- Adapter出力（Provider固有）→ Response Mapperが CanonicalResponse へ変換。
- FinishReason正規化: `completed | length_limit | tool_call | content_filtered | cancelled | error` の6値。
- Usage正規化: { input_tokens, output_tokens, total_tokens, cached_tokens?, reasoning_tokens? }。Providerが返さない場合はTokenizer推定し `usage.estimated=true` を付与。
- エラー正規化: 共通エラーコード（13章）へマップ。Provider固有コードは `provider_detail` に保持（Audit用、利用側応答には含めない設定可）。

## 2.10 Streaming Flow

```
1〜8c: Request Flowと同一（Cacheは既定バイパス）
8d'. adapter.stream() が Provider ストリームを開き、
     Streaming Engine が正規化チャンクへ変換して中継
     チャンク種別: message_start / content_delta / tool_call_delta /
                   usage / message_end / error / heartbeat(15s)
9'.  ToolCallデルタはStreaming Engineが組立て、完結時に確定イベント
10'. message_end 受信後に Usage確定 → Cost算出 → Turn永続化
```

- **バックプレッシャ**: クライアント送信バッファ超過時はProvider読取を一時停止（pull型）。バッファ上限256KB。
- **エラー時**: 最初のチャンク送出**前**の失敗はFallback対象。送出**後**の失敗はFallback不可 → `error` チャンク送出＋接続終了（部分応答はAuditに記録）。
- **切断時**: クライアント切断を検知したらProviderへキャンセル伝播。Usageは受信済分で確定。
- **タイムアウト**: ストリームアイドル（チャンク間）既定60s、全体既定300s。

## 2.11 Retry仕様

| 項目 | 既定値（Policyで上書き可） |
|---|---|
| 最大試行回数（同一候補内） | 3（初回含む） |
| バックオフ | 指数: base 200ms × 2^n、上限 5s、full jitter |
| Retry-Afterヘッダ | Provider指示があれば優先（上限10s） |
| タイムアウト予算 | リクエスト全体timeout（既定60s）から消費。残余不足なら即Fallback |
| 冪等性 | 冪等キー（クライアント指定 or 自動生成）で二重実行防止 |

**エラー分類とリトライ可否**:

| 分類 | 例 | 同一候補Retry | Fallback | CB記録 |
|---|---|---|---|---|
| TRANSIENT | ネットワーク断、5xx、timeout | ○ | ○ | ○ |
| RATE_LIMITED | 429 | ○（Retry-After準拠） | ○ | △（連続時のみ） |
| INVALID_REQUEST | 4xxバリデーション | × | × | × |
| AUTH_ERROR | 401/403 | ×（Credential検証を起動） | ○ | ○ |
| CONTENT_FILTERED | セーフティ拒否 | × | ×（既定。Policyで○可） | × |
| MODEL_ERROR | 出力Schema違反 | ○（是正プロンプトで最大2回） | ○ | × |
| PROVIDER_UNAVAILABLE | 503、CB Open | × | ○ | ○ |

## 2.12 Fallback仕様

- Fallback ChainはRouting確定時に固定（実行中の再ルーティングはしない。ただしCB Open化した候補はスキップ）。
- 移行条件: 上表でFallback=○のエラー、かつタイムアウト予算残 > 次候補の最低所要見込み（p50レイテンシ）。
- 各段で `FallbackExecuted{ from, to, reason }` を発火。
- 全段失敗時: 最後のエラーを正規化して返却 + `RequestFailed` 発火。
- Streamingは初回チャンク送出前のみ対象（2.10）。
- Prompt再構築: 次候補のModel制約（context window差）に合わせContext Managerが再圧縮。

## 2.13 Circuit Breaker仕様

- 単位: (provider_id, model_id) ペア。状態は共有ストアに保持し全ノードで共有。
- CLOSED → OPEN: 直近30秒のスライディングウィンドウで、リクエスト数 ≥ 10 かつ 失敗率 ≥ 50%（CB記録対象エラーのみ）。
- OPEN → HALF_OPEN: 30秒経過後（連続Open回数に応じ指数増、上限10分）。
- HALF_OPEN: 試行を最大3並行まで許可。3連続成功 → CLOSED、1失敗 → OPEN。
- 状態変化時 `CircuitBreakerStateChanged` 発火。

## 2.14 Cache仕様

| 種別 | キー | 対象 | TTL既定 | 無効化 |
|---|---|---|---|---|
| Request Cache（冪等） | idempotency_key + tenant_id | 全Capability | 24h | TTLのみ |
| Response Cache | hash(tenant_id + capability + canonical_request正規化JSON + model_alias解決結果) | temperature=0等の決定的要求、embedding、image_analysis | 1h（Capability別設定） | TTL / Alias切替時に該当Alias配下を一括無効化 / Admin API |

- 非決定的要求（temperature>0、Streaming）は既定でResponse Cache対象外。
- キャッシュ応答には `cached=true, cached_at` を付与。Usage/Costは記録するがProvider呼出コストは0。
- ストア実装はSPI（既定: 分散KVS、差替可）。

## 2.15 Session仕様

- Session{ session_id, tenant_id, principal（CIAP subject）, attributes{}, created_at, expires_at, status(ACTIVE/EXPIRED/REVOKED) }
- 有効期限既定24h（スライディング更新可）。SessionはConversationを0..n保持。
- Sessionは任意（ステートレス利用可）。Conversation利用時は必須。

## 2.16 Conversation仕様

- Conversation{ conversation_id, session_id, title?, status(ACTIVE/ARCHIVED/DELETED), turns[] }
- Turn{ turn_id, seq, role(system/user/assistant/tool), content parts[], model_used, usage, created_at }
- Context組立: Context Managerが (1) System Prompt (2) Memory注入分 (3) 履歴 (4) 今回入力 を合成し、Model context_window − max_output_tokens − 安全マージン(5%) に収まるよう圧縮。
- 圧縮戦略（SPI差替可）: ①古いTurnから切詰め（既定） ②要約圧縮（古い区間をModelで要約し1 Turn化） ③重要度スコアによる選択保持。
- 削除: 論理削除 → 保持期間経過後に物理削除。テナント即時物理削除API提供。

## 2.17 Memory仕様

- Memory{ memory_id, scope(tenant/user/agent), content, embedding_vector, importance, created_at, last_accessed_at, ttl? }
- 保存: 明示API（`memory` Capability）または Conversation要約からの自動抽出（Policy有効時）。
- 注入: Chat実行時に今回入力のEmbeddingで類似検索（top-k既定5、類似度閾値0.75）し、System Prompt後方へ注入。
- ストアはベクトル検索可能なリポジトリ（SPI）。

## 2.18 Audit仕様

- Audit EngineはEvent Busを購読し、追記専用ストアに保存（同期パスに書込を置かない）。
- AuditRecord{ audit_id, request_id, trace_id, tenant_id, principal, capability, model_alias, resolved_provider, resolved_model, routing_decision, request_digest（本文は既定ハッシュのみ）, response_digest, status, error_code?, usage, cost, duration_ms, retries, fallbacks, timestamp }
- 本文保存はテナントポリシーでopt-in、保存時はPIIマスキングパイプラインを通す。
- 検索API: 期間・テナント・Provider・エラー種別・request_idで検索（Read Model使用）。
- 保持: 既定400日、WORMストレージ。

## 2.19 Monitoring仕様
