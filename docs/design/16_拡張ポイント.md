# 16. 拡張ポイント

AI Provider Abstraction Platform（APAP）設計書 第16章

すべての拡張はSPI（interface）+ 宣言的バインド（3.15のDI設定）で実現する。コア改変を伴う拡張は設計違反とみなす。

---

## 16.1 Plugin（Provider Adapter）

| 項目 | 内容 |
|---|---|
| SPI | `ProviderAdapter`（3.3.2） |
| 追加方法 | Plugin配置 → scan → 署名検証 → ロード（15.1） |
| ライフサイクル | scan → verify → LOADED → initialize → (稼働) → drain → shutdown → UNLOADED。不適合は QUARANTINED |
| 互換性 | `spi_version` レンジ宣言。SPIはsemver管理（後方非互換はメジャー更新のみ） |
| 隔離 | 分離クラスローダ/サイドカープロセス。自Provider Credential以外へのアクセス不可、egress許可先限定 |

## 16.2 Routing

| 拡張点 | SPI | 例 |
|---|---|---|
| スコアリング戦略 | `RoutingStrategy.score(candidate, ctx)` | 品質ベンチマーク重視、時間帯別重み、SLA逆算 |
| 候補フィルタ | `RoutingPolicyEvaluator` | 独自コンプライアンスフィルタ（データ主権等） |
| 負荷分散 | `LoadBalancer.choose(top)` | LeastConnections、レイテンシ予測ベース |
| Sticky規則 | `StickyResolver` | ユーザー単位固定、ABテスト割付 |

登録: 実装をPluginとして配置し `apap.routing.strategy: <name>` で選択。テナント別に異なるStrategy指定可。

## 16.3 Policy

| 拡張点 | 内容 |
|---|---|
| Rule条件式 | `Expression` 評価器はSPI。既定は比較・論理演算。独自関数（例: `businessHours()`）を `ExpressionFunction` として追加可能 |
| Policyスコープ | 4階層（PLATFORM/TENANT/WORKFLOW/USER）は固定。スコープ内のルール語彙は拡張可 |
| 動的Policy | `CostThresholdExceeded` 等のイベントを購読して `PolicyUpdated` を発行する自動Policy Controllerを追加可能（例: 予算超過時に低コストAliasへ自動切替） |

## 16.4 Cache

| 拡張点 | SPI | 例 |
|---|---|---|
| ストア実装 | `CacheStore`（get/put/delete/scanByPrefix） | 分散KVS（既定）、ローカル+分散2層 |
| キー戦略 | `CacheKeyStrategy` | 正規化JSONハッシュ（既定）、**セマンティックキャッシュ**（Embedding類似で近傍hit） |
| 対象判定 | `CacheabilityPolicy` | temperature=0のみ（既定）、Capability別カスタム |
| 無効化 | `InvalidationHook`（AliasChanged等のイベント購読） | 独自無効化トリガ |

## 16.5 Retry

| 拡張点 | SPI | 例 |
|---|---|---|
| バックオフ戦略 | `RetryStrategy.nextDelay(attempt, error, retryAfter)` | 指数+jitter（既定）、固定、Adaptive（成功率学習） |
| エラー分類 | `ErrorClassificationService` の分類表はProvider共通。Adapter側で `AdapterException` 分類を精緻化することで挙動を制御 |
| 予算管理 | `TimeoutBudgetPolicy` | Capability別予算配分 |

## 16.6 Monitoring

| 拡張点 | SPI | 例 |
|---|---|---|
| Metrics Exporter | `MetricsExporter` | OpenMetrics（既定）、独自基盤push |
| Trace Exporter | `TraceExporter` | W3C準拠基盤へ送出 |
| ヘルス判定 | `HealthEvaluator` | 判定閾値（2.6.3）の差替、外形監視統合 |
| アラートルール | イベント購読型 `AlertRule` | 独自通知チャネル |
| マスキング | `MaskingStrategy` | 正規表現PII（既定）、ML基盤マスク |

## 16.7 Prompt

| 拡張点 | SPI | 例 |
|---|---|---|
| Pipeline Stage | `PromptStage.apply(draft, ctx)` を任意位置へ挿入 | 用語統一Stage、社内ガイドライン注入Stage、多言語正規化Stage |
| Validation規則 | `PromptValidator` | インジェクション検査強化、業界別禁止語 |
| Optimization | `PromptOptimizer` | トークン圧縮アルゴリズム差替 |
| Template関数 | `TemplateFunction` | カスタム変数解決（例: 現在時刻、テナント語彙） |
| 圧縮戦略 | `CompactionStrategy`（2.16） | 要約圧縮、重要度選択 |

## 16.8 Provider

15.1参照。補足の拡張余地:

| 拡張点 | 内容 |
|---|---|
| 認証方式 | `AuthHandler` SPI。api_key / oauth2_client_credentials / signed_request（既定同梱）に加え、独自方式を追加可能。Adapterは `auth_type` 宣言のみで利用 |
| Secret Store | `SecretStore` SPI。KMS/Vault互換実装を差替可能 |
| Usage/Cost取得 | `fetchUsage / fetchCost` 任意実装。Provider側請求とAPAP側算出の突合ジョブ（Reconciliation）を追加可能 |
| デプロイ形態 | プロセス内Plugin（既定）⇄ サイドカー（gRPCブリッジ）。SPI契約は不変 |

## 16.9 Capability

15.3参照。補足:

| 拡張点 | 内容 |
|---|---|
| Capability Registry | JSON Schema登録のみで新Capabilityを定義（PREVIEW→GA） |
| 汎用実行口 | `POST /v1/execute { capability_id, input }` により、専用エンドポイント追加なしで新Capabilityを即時利用可能 |
| Mapper拡張 | `CapabilityMapperExtension` SPIで特殊変換を追加 |
| 将来Capability | video_generation / fine_tuning は本SPI構造の範囲で追加可能（ジョブ型Capabilityとして `batch` と同じ非同期パターンを再利用） |

## 16.10 拡張時の不変条件（全拡張共通）

1. 利用側公開API（apap-api）の後方互換を破壊しない。
2. Domain層の依存ゼロ原則を維持する（拡張はPort実装として追加）。
3. 拡張実装は必ずContract Testに合格する。
4. Credential・PIIの取り扱い規約（FR-SEC-001, NFR-SEC-001）は拡張実装にも適用される。
5. 拡張の有効化・無効化は宣言的設定で行い、変更はAuditに記録される。
